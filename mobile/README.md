# RAFTAAR EXPRESS — Rider App (Flutter, Android)

Rider-facing mobile client for the courier platform in this repo (`backend/` — FastAPI).
This is **Phase 1** of a phased build against the full enterprise rider spec — see
[Roadmap](#roadmap--whats-not-here-yet) below for what's deliberately deferred and why.

## What's implemented

- Login (email + password), JWT session with automatic access-token refresh, secure token storage
- Dashboard: today's stats, availability (online/offline) toggle, COD wallet (held/limit/warning/frozen)
- Deliveries list (offers / active / history tabs)
- Accept/decline pickup and last-mile delivery offers
- Confirm pickup (GPS-stamped)
- Complete delivery: OTP + photo + GPS proof of delivery (all three required, matches the backend's
  `POST /rider/deliveries/{id}/proof-of-delivery` contract)
- Mark a delivery failed with a reason (matches the reasons list in the spec)
- Foreground GPS ping to the backend while online, so `/rider/location` stays current
- A lite offline queue: if "Confirm Pickup" or "Mark as Failed" is submitted with no connectivity,
  it's queued locally and retried automatically once the connection returns
- A permanently-denied location/camera permission surfaces a clear message with a button straight to
  the app's Settings page, instead of a dead-end error
- Unit tests for the model parsing / formatting logic and a widget test for the login screen
  (`flutter test`)

## Prerequisites

- [Flutter SDK](https://docs.flutter.dev/get-started/install) (stable channel) — **not installed on
  the machine this app was scaffolded on**, so the Android build files here were hand-written rather
  than generated by `flutter create`, and the Gradle wrapper's binary jar is missing.
- Android Studio (or just the Android SDK + a device/emulator)
- The backend running locally (`backend/README.md` / root `README.md` — `docker-compose up --build`,
  then run migrations + `python seed_roles.py`) with at least one seeded **rider** account you can log
  in with. `backend/seed_users.py` / `backend/seed.py` are a starting point if you need to create one.

## First-time setup

```bash
cd mobile/rider_app

# Backfills whatever Flutter's own tooling manages that couldn't be hand-written here —
# most importantly android/gradle/wrapper/gradle-wrapper.jar (a binary) and android/local.properties.
# This does NOT overwrite the pubspec.yaml / lib/ / android files already in this folder.
flutter create --platforms=android --org com.raftaarexpress .

flutter pub get
```

## Running against the backend

The API base URL is compiled in via `--dart-define` (see `lib/core/config/env.dart`), defaulting to
`http://10.0.2.2:8000/api/v1` — the Android emulator's alias for your host machine's `localhost:8000`.

```bash
# Android emulator, backend running on the host via docker-compose (default, no flag needed):
flutter run

# Physical device on the same Wi-Fi as your backend - use your machine's LAN IP instead:
flutter run --dart-define=API_BASE_URL=http://192.168.1.50:8000/api/v1

# Release build:
flutter build apk --dart-define=API_BASE_URL=https://your-deployed-api.example.com/api/v1
```

Debug builds allow plaintext HTTP (`android/app/src/debug/AndroidManifest.xml`) so `http://10.0.2.2:8000`
works against targetSdk 34's default cleartext block; release builds do not get that override, so a
deployed backend needs to be served over HTTPS.

## Tests

```bash
flutter test
```

Covers `Formatters`, the `Order`/`RiderProfile` JSON parsing (`test/models_test.dart`), and a
`LoginScreen` widget test (`test/login_screen_test.dart`) that exercises validation and the error path
against a fake `AuthService` — none of it touches the network or secure storage, so it runs without a
device/emulator.

## Architecture

- `lib/core/` — networking (Dio client with auth-refresh interceptor), theme (matches the Next.js
  frontend's navy/orange RAFTAAR EXPRESS palette), formatting utils, shared widgets
- `lib/models/` — plain Dart classes mirroring the backend's Pydantic schemas
- `lib/services/` — one class per backend router surface the app talks to (`AuthService`,
  `RiderService`), plus `LocationService` (GPS ping loop) and `OfflineQueueService`
- `lib/features/<name>/` — one folder per screen area, each with its own `ChangeNotifier` provider
  (via the `provider` package) and screen(s)
- State is plain `provider`/`ChangeNotifier` — no code generation, so nothing here requires a build
  step beyond `flutter pub get`

A backend addition was needed for this: **`GET /rider/deliveries/{order_id}`**
(`backend/app/api/v1/rider.py`) — the rider previously only had a list endpoint with no COD/payment
detail. It mirrors the existing customer-facing detail endpoint pattern and returns `OrderDetailOut`.

`minSdk` is set to 26 (Android 8.0+, `android/app/build.gradle`) rather than Flutter's usual 21/23
floor, so every supported device gets proper adaptive-icon support with no legacy raster fallback
needed. The pre-8.0 install base for a new app in 2026 is negligible.

## Known limitations (Phase 1)

- **GPS is foreground-only.** There's no Android foreground service, so location pings stop if the
  app is backgrounded or killed. Full background tracking needs a foreground service + battery
  optimization handling — deferred.
- **The offline queue only covers delivery status updates** (confirm pickup / mark failed), not the
  proof-of-delivery submission (which needs a live OTP round-trip with the server) or GPS pings
  (already best-effort/fire-and-forget). It's a narrow, honest "lite" version of spec sections 40-46,
  not the full local-SQLite-mirror-with-conflict-resolution engine described there.
- **No push notifications.** New offers/approvals require pulling to refresh.
- **The launcher icon is a placeholder** (a simple vector arrow mark on the brand navy, wired up as a
  proper Android adaptive icon at `android/app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml`) —
  swap the artwork for real branding before shipping, the plumbing is already correct.

## Roadmap — what's not here yet

This app intentionally covers only what the current backend supports well. The full spec pasted into
the original request describes a much larger enterprise system; the rest is planned as later phases,
each needing backend work first:

1. **Status change request/approval workflow** (spec §5-6) — riders currently toggle availability
   directly; the request→Hub/Admin-approval→history flow needs new backend models + endpoints.
2. **Parcel lock/unlock system** (spec §9-19) — the nearest-eligible-parcel algorithm, locked-parcel
   UI, and the unlock-request/approval flow. Backend currently exposes all assigned deliveries at
   once with no locking concept.
3. **Bus manifest scanning for riders + RTO/crate/return-batch workflow** (spec §28-39) — hub-side
   manifest/bus_network code exists in the backend already; rider-facing scan-in/scan-out and RTO
   creation don't yet.
4. **Full offline-first architecture** (spec §40-46) — local SQLite mirror of assigned parcels,
   generic event queue, conflict logging, immutable audit log. Today's app is online-first with a
   narrow offline fallback (see above).
5. **Push notifications, support tickets, earnings breakdown** (spec §49-51).
6. **Admin/Hub live-tracking dashboards** — out of scope for this Flutter app; belongs in
   `frontend/app/admin` and `frontend/app/hub` (the Next.js app), which can already consume
   `/rider/location` once built.
7. **Infra**: load balancing, autoscaling, API rate limiting, Redis caching, DB indexing (spec §53-55)
   — explicitly deferred per the scoping conversation that kicked this off; revisit once the feature
   surface is further along.
